## 已确认的启动现象

使用实际安装的程序、独立空工作区和独立 WebView2 数据目录，以进程所属窗口的可见状态计时，不连接 SSH，不启动 AI API。单位为秒；停留时间为启动页首次可见至主窗口首次可见，不是进程启动至主窗口的总时间。

存在约 6 秒的慢启动，也存在不足 1 秒的启动页停留；复用缓存仍然可能慢，不能把现象简单归因为首次缓存创建。少量样本不代表 p50/p95，前两个样本采集期间有后台编译。

本机用户原有启动日志显示工作区初始化最近为 1–2 ms；隔离程序为 1–4 ms。API 自动启动在后台任务运行，重试退避释放生命周期锁，主窗口显示不等待它。

## 修复前的关键路径与证据边界

修复前路径：Tauri 创建隐藏的 `main` 和独立 `splash` WebView → 首屏 React/antd 加载 → 延迟导入 App → 注册配置/API 状态监听 → `useAppBootstrap.signalFrontendReady` 等两次 requestAnimationFrame → `frontend_ready` IPC → Rust 显示主窗口、关闭启动页。

确认的结构问题是：显示主窗口依赖隐藏窗口中的动画帧调度，以及与显示无关的事件订阅完成。显示门槛没有独立于绘制调度的完成路径；隐藏/遮挡场景下帧调度本身不是可靠的就绪信号。这是需要优先修正的时序依赖，但尚未捕获安装程序慢样本中每个回调的起止，不能声称它独占全部额外 5 秒。

首屏主要 JS 资源约 1.57 MB（antd 1056832 字节、App 512571 字节），还存在首屏到 App 的串行导入。在同源前端的独立 Release 诊断程序中，资源读取约 9–55 ms，配置 IPC 合计约 4–6 ms，正常样本显示握手在页面导航后约 0.6 s 发起；捕获到首次绘制相关长任务约 83–99 ms，两个动画帧回调一例约等待 99 ms / 3 ms。该诊断进程启用了远程调试，不能用这些正常样本替代原安装程序的慢样本，也不能把 5 秒直接解释为 JavaScript 解析时间。

## 调查时选定的修复方案

1. 将主窗口显示握手从双 requestAnimationFrame 改为应用外壳完成提交后的幂等通知。事件订阅继续约束配置读取和状态同步，但不再约束窗口显示；保留加载中/失败界面。
2. 记录进程入口、主页面加载、App 提交、订阅完成、显示请求和实际 show 的分段时间，补齐当前慢样本证据缺口。
3. 拆分首屏 antd 大块与非首屏组件，把终端等重模块延迟到使用时，避免简单增加 GPU/AVX2 开关。
4. 对相同 Release、相同数据分别采集冷/热启动、隐藏/遮挡场景；验证慢启动尾部下降，主窗口首次显示后可操作，事件不丢失、无白屏或重复初始化。未实施前不承诺具体秒数。

## 启动修复实现

- 主窗口外壳提交后立即发送幂等 `frontend_ready`，移除隐藏窗口的双 animation frame 等待，不再等待 App 大模块和事件订阅。Rust 只接受主窗口握手，退出中和重复调用不重新抢焦点，show 失败允许重试。
- 配置初始化仍在早期配置/API 监听注册后执行，保留先订阅再获取快照的顺序。移除显示握手后重复的 API 状态查询。
- 移除全局 antd 大块，按模块的实际静态依赖分包。SessionWorkspace、MigrationGate、设置和编辑器等重模块按需加载；独立编辑器通信逻辑抽出后，App 的清理回调不再静态引入 FileManager。
- 构建清单中，入口外壳静态 JS 为 199767 字节，入口与 App 的静态依赖去重后为 684990 字节。此前仅 antd + App 两大块就有 1569403 字节；因此初始工作区 JS 至少减少约 56%。这是未压缩传输编码的构建文件大小，不是 JS 解析 CPU 耗时。
- 启动日志新增进程入口相对时间、页面加载、外壳/App 提交、监听完成、工作区就绪和实际窗口显示。前端导航时间与原生收到通知时间同时记录，能够区分前端尚未完成与原生事件循环延迟。

## 复测补充定位：同步系统信息查询阻塞 UI

只实施上述前端修复的 Release 中，主窗口在 Rust 入口后约 0.58 秒已显示，但连续三个样本的工作区就绪通知仍到 6.062–6.170 秒才由原生处理。对应的前端 `navigation_ms` 只有 534–570 ms，不能将这段差值解释为 JS 解析。

追踪发现启动的 `app_info` 是同步 Tauri 命令，在 UI 线程调用 `friendly_os_name`，再执行 `Command::new("cmd").args(["/C", "ver"]).output()`。诊断样本中，HelM 所属的同一个 `cmd.exe` 从启动后 1.374 秒至 6.271 秒持续存在；另外的窗口 WM_NULL 探测捕获到持续不响应。单独在 PowerShell 中隐藏运行 `cmd /C ver` 仅约 47 ms，说明不能用控制台测量替代桌面程序里的子进程启动路径。尚未进一步区分控制台分配、系统终端宿主或系统策略各自占比。

已将 Windows 版本查询改为直接调用 `RtlGetVersion`，不再启动 cmd.exe；系统名称按进程缓存。`app_info` 改为异步命令，系统/路径查询放入阻塞工作线程，避免其他平台首次元数据读取也阻塞 UI。新增 `Startup app info ready: duration_ms=...` 记录。

## CPU 指令集边界

WebView2 的 V8 负责 JS 解析和编译，并按运行机器使用其支持的 CPU 优化。应用不能通过 Rust 的 AVX2 编译开关让 V8 的 JS 解析器改用 AVX2。此次减少实际需要加载和解析的 JS，并删除阻塞调用；没有声称启用新的 SIMD 解析器，也没有增加全局 `target-cpu=native` 或 `+avx2`。
